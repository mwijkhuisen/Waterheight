# ADR-0021: Home hosting behind a Cloudflare Tunnel

- **Status:** Accepted (owner, 2026-10-12; issue #109, `docs/plan/PHASES.md` §50). It widens D20 (`docs/plan/PHASES.md` §6.1).
- **Date:** 2026-10-12
- **Revisit:** when the site moves to a VPS with a public address (the tunnel is then optional and `RWS_EDGE=direct` is the default again), or after the first flood season in tunnel mode, whichever comes first.

## Context

- **The host is a home line.** Production runs on the owner's machine behind a home router (KG-228). Every visitor reaches it through a Caddy reverse proxy on the LAN and the router's forwards of TCP 80 and 443 (and UDP 443); `RWS_TRUSTED_PROXIES` names that proxy so the limiter and the masked log see visitors (`docs/runbooks/api.md` §6). The home address is public, changes with the line and is a direct target.
- **D20 covers less than this.** D20 arms a CDN pull zone for `/tiles/*` and `/assets/*` only, as a flood fallback (`docs/runbooks/cdn-break-glass.md`). Its origin stays reachable directly, so R-097 makes origin authentication a precondition of arming it.
- **The old domain goes.** The public domain moves to `waterradar.io`, whose zone has been on Cloudflare since registration (owner, 2026-10-12). `docs/runbooks/domain-change.md` does that step in direct mode, before this one.
- **A tunnel needs no inbound port.** `cloudflared` dials out to Cloudflare and carries the visitors' requests back over that connection, so the router can forward nothing but WireGuard (UDP 51820).

## Decision

1. **One switch, `RWS_EDGE=direct|tunnel`** in `/etc/rws/rws.env`; `direct` (or unset) is today's stack, byte for byte. `rws_compose` in `deploy/bin/rws-lib.sh` stops before docker runs on any other value. It is a `RWS_*` line, because `load_env` takes no other kind; a compose profile in `rws.env` is not possible.
2. **An overlay, `deploy/compose.tunnel.yaml`,** added by `rws_compose` only in tunnel mode (the pattern of `RWS_OWNER_SITE=on` and `compose.owner.yaml`). It adds the service `cloudflared` (image `cloudflare/cloudflared:2026.9.3@sha256:…`, BOM row, non-root, read-only, `cap_drop: ALL`, `no-new-privileges`, 256m, 1 cpu, 128 pids, a shell-free healthcheck, `tunnel run --token-file`) and changes `caddy`.
3. **Network design.** `cloudflared` is on two networks and nothing else shares them with it but `caddy`: `tunnel` (bridge `rws-tunnel`, IPv4 only, not internal: its egress to Cloudflare and DNS) and `tunnel_edge` (internal, the link to `caddy:80`, `cloudflared` at the fixed address 172.30.41.10). It is on no other network: not `edge` (`api` trusts `X-Rws-Client` from any peer, T-API-3), not `db`, not the owner's. `api`, `api-owner`, `caddy-owner` and `db` are never on either tunnel network (`deploy/tests/hardening.sh`, `test/compose-tunnel.test.ts`). Whatever the Cloudflare dashboard says, `cloudflared` can reach `caddy:80` and Cloudflare, nothing else.
4. **Plain HTTP only inside the stack.** In tunnel mode Caddy serves one `:80` server (`RWS_SITE_SCHEME=http`: no TLS listener, no ACME, no certificate); the site address is `{$RWS_SITE_SCHEME:https}://{$RWS_DOMAIN}` and the 421 catch-all and the per-edge lines come from `edge-https.caddy` or `edge-http.caddy`, imported at the top of `site.caddy`; each also defines the snippet `edge_site`, imported in the site block: empty in direct mode, and in tunnel mode a `no-store` 308 to `https://` for a request with `X-Forwarded-Proto: http`, so a plain-HTTP visit that Cloudflare forwards ("Always Use HTTPS" switched off by mistake) is redirected, never served. Direct mode keeps TLS, HSTS and the redirect, and no `RWS_EDGE` mistake can serve plain HTTP to the internet: Caddy publishes only `127.0.0.1:80` in tunnel mode (for the deploy smoke test), and any other scheme value stops Caddy.
5. **The trusted proxy is `cloudflared`'s fixed /32.** Caddy's TCP peer is `cloudflared`, not a Cloudflare range. `RWS_TRUSTED_PROXIES` is set by the overlay to `172.30.41.10/32` (never a /24 that holds the bridge gateway, which is the host). The existing `trusted_proxies_strict` rule takes the right-most untrusted `X-Forwarded-For` address, which Cloudflare appends, so a client-sent prefix, `CF-Connecting-IP` or `X-Rws-Client` never chooses the limiter key.
6. **The token is a file secret.** `/etc/rws/secrets/cf_tunnel_token`, `root:61012 0440`, read with `--token-file`; never in `rws.env`, an environment variable, `docker inspect`, a log or a ticket (`--token` and `TUNNEL_TOKEN` take precedence over the file, so neither is ever set). T-EDGE-1; rotation in `docs/runbooks/secrets-rotation.md`.
7. **Egress.** One rule in `deploy/host/nftables.conf`: TCP and UDP 7844 from the bridge `rws-tunnel` to the set `cftunnel4` (198.41.192.0/24, 198.41.200.0/24), and no 443 for it (`--no-autoupdate`: the optional update and post-quantum endpoints stay blocked).
8. **Cache rules at Cloudflare** (`docs/runbooks/edge-switch.md`): `/tiles/*` bypasses the cache (on a cold miss of a cacheable object Cloudflare drops `Range`, which our tile routes answer with 416); `/data/*` is eligible and honours the origin's `Cache-Control` (our 404s carry none, so they are never cached); `/assets/*` is eligible and uses the origin's `Cache-Control` if present and bypasses if not (the real assets are immutable; our `/assets` 404 carries no `Cache-Control` and must not take Cloudflare's status TTL). Everything else is default, which caches no HTML, JSON, `/api` or `/status`.
9. **Privacy first.** `RWS_CDN_NAME=Cloudflare` makes the privacy page name Cloudflare first, before anything else it says about processing: every request passes through it, it sees every request with the visitor's address, it caches only `/assets` and `/data`, it is a US company and transfers rest on the EU-US Data Privacy Framework. The strong text appears only for exactly `Cloudflare`; another name gets a neutral text. The page is checked in NL and EN before the DNS switch, and the owner approves the text (E5). The committed default stays "no CDN".
10. **The owner host is never behind Cloudflare.** `owner.<domain>` has no public DNS record and no tunnel route; the tunnel has one public hostname, the site's. `verify-prod --edge cloudflare` still checks that DNS has no record for it and that the owner listener (443 and 8443) gives an edge only a refusal, a failed handshake or an answer without the owner site's exact headers (`Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow`; a Cloudflare error page is the safe state).
11. **The dashboard is not code, so a check watches it.** The settings that would inject scripts, set cookies or add `NEL`/`Report-To` (invariant 7, the CSP) are listed in the runbook; `scripts/verify-prod.sh <domain> --edge cloudflare` has an `edge` group that fails on each of them. There is no Terraform for Cloudflare. The Cloudflare account itself is a root of trust beside the token (R-106); its controls are in the runbook, not in code.

## What it widens in D20

D20 allowed a pull zone for two static trees. In tunnel mode **the whole public host sits behind Cloudflare**: the HTML, the JavaScript, the API and the status files pass through it, not only the tile and asset trees. D20's rules still hold for what is cached (nothing but `/assets` and `/data`; no `4xx`, no `5xx`, no `/api`, no `/status`), the privacy page names the CDN first, and no third-party tile host such as OpenFreeMap is ever used (invariant 7, ADR-0016); R2 stays the break-glass of D20. R-097 ("the origin stays reachable directly") is met structurally in tunnel mode, since the origin publishes loopback only and the router forwards nothing; it still binds the direct-mode break-glass. Tunnel mode carries the egress of `/assets` and `/data` at Cloudflare's edge, while the tiles bypass the cache and still use the home uplink (`docs/capacity.md`); the D20 numbers decide whether that is enough.

## Alternatives rejected

- **A compose profile in `rws.env`** (`COMPOSE_PROFILES`, `CF_TUNNEL=1`): `load_env` accepts `RWS_*` lines only and dies otherwise.
- **`auto_https off` for the tunnel:** measured with Caddy 2.11.4 (`caddy adapt`): the site still binds `:443` with a TLS policy and no certificate. The scheme in the site address gives one `:80` server and no ACME; for the same reason the catch-all `:80, :443` moved to per-scheme files.
- **Trusting Cloudflare's address ranges:** Caddy's TCP peer is `cloudflared`, so the ranges would match nothing, and a shared range is what R-097 warns about.
- **Putting `cloudflared` on the existing `edge` network:** it is internal (no way out) and holds `api`, whose `X-Rws-Client` is trusted from any peer; it would also give a compromised connector a path to `api:8080`.
- **A /24 as the trusted proxy:** the bridge gateway is the host, so a host or LAN request to the published loopback port would be trusted with its `X-Forwarded-For`.
- **Cloudflare Access, WARP or private-network routes on the tunnel:** not needed, and each would add a route into the stack.

## Consequences

- **Cloudflare sees every request** (path, query string, visitor address) and could alter any answer, the JavaScript included. The privacy page says so before the switch; T-CDN-1 is widened and the `edge` group catches injections and cookies, not a malicious edge.
- **Availability is the home line's and the power's** (R-102, owner decision: same host). Cloudflare keeps serving cached `/assets` and `/data` for a while, and nothing else.
- **The watchdog's `cert` check reads Cloudflare's edge certificate,** not Caddy's. In tunnel mode Caddy's Let's Encrypt certificate is not renewed, so a **rollback to direct needs port 80 forwarded again** for the HTTP-01 challenge if that certificate has expired, and the CAA records must allow Let's Encrypt as well as Cloudflare's authorities (`docs/runbooks/edge-switch.md`).
- **HSTS preload (ADR-0020) only after the tunnel is stable;** a preloaded name cannot be served over plain HTTP, and a rollback or a Cloudflare change would be a one-way door.
- **Limits of the free plan.** Cloudflare's Service-Specific Terms (2026-09-28) restrict "disproportionate large files" served without caching, which the tile ranges are (R-103). R2 stays the D20 break-glass, not a plan.
- **The real `cloudflared` never runs in CI** (a stand-in does): its start with `--token-file`, its `tunnel ready` healthcheck and QUIC/HTTP2 on 7844 are first proved at cutover (KG-347).
